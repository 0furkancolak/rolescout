# ADR 0001 - Domain Model and Database Schema

Status: Accepted
Date: 2026-10-17

## Context

Phase 2 defines the persistent model for users, workspaces, job listings and
application tracking. PostgreSQL is the source of truth. The model must support
multi-user installations with workspace isolation (Phase 4), source ingestion
with deduplication (Phase 6), and application history that is never overwritten.

## Decisions

### Identifiers and time
- Primary keys are `UUID` generated by PostgreSQL (`gen_random_uuid()`), so IDs
  are not guessable and can be created without coordination.
- All timestamps are `TIMESTAMPTZ` and written in UTC. `created_at` is set by a
  default; `updated_at` is maintained by the `rolescout_set_updated_at` trigger.

### Ownership
- **Global data** (shared by every workspace): `job_sources`, `jobs`,
  `job_source_listings`. They are written by the worker and read by everyone.
- **Workspace data**: `saved_jobs`, `applications`, `application_attempts`,
  `application_events`, `tags`, `application_tags`, `notes`.
- **Users** belong to workspaces through `workspace_memberships` with a role of
  `owner` or `member`. Creating a workspace always creates the owner membership
  in the same transaction.

### Workspace isolation in the schema
Workspace-owned tables carry `workspace_id`, and links between workspace-owned
rows use composite foreign keys on `(workspace_id, id)`. A tag from workspace A
therefore cannot be attached to an application in workspace B, and a note cannot
point at another workspace's application, even if application code has a bug.
Authorization (who may act in a workspace) is still enforced by the API in Phase 4.

### Jobs and deduplication
- `jobs` is the canonical, deduplicated job. `dedupe_key` is unique and is
  computed by the ingestion layer (Phase 6) from normalized attributes.
- `job_source_listings` records each place a job was seen: source, the source's
  own `external_id` (unique per source), the original URL, and the source's
  posted/updated times. Ingestion time (`last_ingested_at`) and source update
  time (`source_updated_at`) are stored separately.
- Sources are created disabled (`enabled = false`); enabling requires the
  permission and terms review described in `docs/PLAN.md`.

### Applications and history
- A workspace has at most one `application` per job; it holds the current
  `status`.
- Each actual submission is an `application_attempt` with a sequential
  `attempt_number`. Attempts are never overwritten - re-applying adds a row.
- `application_events` is an append-only log (status changes, interviews,
  follow-ups, deadlines, attempts). Every status change is written together with
  its event in one transaction by the repository.
- Status values: `planned`, `applied`, `interviewing`, `offer`, `accepted`,
  `rejected`, `withdrawn`. Transition rules are a business rule for the
  application layer (Phase 3), not a database constraint.

### Enumerations
Small fixed value sets use `TEXT` with `CHECK` constraints instead of PostgreSQL
`ENUM` types, so adding a value is a simple additive migration.

### Deletion
- Deleting a workspace cascades to all of its data.
- Deleting a user cascades memberships; content authored by the user keeps
  existing with the author reference set to `NULL`.
- Jobs referenced by saved jobs or applications cannot be deleted (`RESTRICT`).

### Migrations
- Forward-only, timestamped files applied by the API at startup.
- The runner holds a PostgreSQL advisory lock so concurrent API replicas do not
  apply the same migration twice.

## Consequences
- Repository methods for workspace data always take a `workspaceID` and filter
  by it, which gives Phase 4 a single place to plug authorization in.
- Dedupe key computation is deferred to Phase 6 and must be stable once data
  exists.
